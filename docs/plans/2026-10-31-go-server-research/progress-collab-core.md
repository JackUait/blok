## Decisions (round 3)

- The journal oracle is a scenario script, not a set of golden files. C# runs each scenario against its real store with an internal `TimeProvider` (new constructor parameter, defaults to the system clock; no published surface) and writes down each answer, the log and the files. Steps that need C# code to make bytes (corrupt a record, a foreign-version manifest, a damaged working set) are written into the fixture as plain `write` steps, so Go needs no copy of that code.
- Cross-reading: Go replays every scenario and must leave the same bytes, so C# reads Go's directories exactly as it reads its own. Go also opens every directory C# left (the `files` of each scenario) and must see C#'s fresh-store `reopen` result.
- Errors are compared by kind and C#'s message. IOException and UnauthorizedAccessException are one kind ("IO", no message): which of the two the OS gives differs between macOS and Linux. Log lines that quote the OS's words for a held lock are cut after "held elsewhere:".
- The fixture holds only what is the same on macOS and Linux (no symlink loops, no chmod, no case-insensitive names); those are Go twins.
- `globFiles` is .NET's `Directory.GetFiles(dir, "stem.*")`: files only, and a bare `stem` also matches (pinned by `a-bare-journal-file-without-a-manifest` and `the-sweep-matches-like-dotnet-globs`).
- `removeFile` is `File.Delete`: a missing file is fine and a directory is an error (Go's `os.Remove` would remove an empty directory).
- Go's zero `MaxUpdateBytes` means the 1 MiB default; C# refuses 0. Negative and above 32 MiB are refused like C#.
- Codec refusals are now `*ArgumentError` with C#'s words (they gained the final period C# has).
- RollBack has no C# test. Go stages a failed fsync through a package seam (`syncJournal`): the record is cut and the retry commits at sequence 1; when the fence moved first, the bytes stay and the session answers "could not be flushed" from then on. Mutation-checked (3 mutants). C# is unproven here.
- A directory at the lock path: Go refuses the open as held elsewhere, which is what C# does on Linux (EISDIR is an IOException there). C# on macOS throws instead (UnauthorizedAccessException). Not in the fixture.
- Linux checked in docker: C# `CollabJournalStoreCaptureTests` passes on `mcr.microsoft.com/dotnet/sdk:10.0` (so the macOS-captured fixture holds on Linux), and the Go journal tests pass on `golang:1.27.3` as a non-root user with python3. GitHub's ubuntu runner has /usr/bin/python3, which the C# python-holder test already needs on Linux CI.
- Test-cache trap: `go test` reused a result while mutating `store.go`; run mutants with `-count=1`.

A test-only seam `YDocConverter.RowKeySource` (AsyncLocal, so parallel xunit classes are untouched) mints grid row keys from a counter in the capture; Go swaps `GenerateRowKey`. The Go test calls `CollectOpsHTML` before `ApplyOps`, as the room does: both plan, and planning mints keys (Screen builds the grids), so the call order shows in the bytes.
- HTML in the edit cases is read by C#'s runtime and recorded with its segments in the fixture; Go builds `Converting` from them, so the apply test needs no runtime.
- Edit values keep each number's text (`sourceNumber`, from `editValue`); `atomicValue` turns it into a float64 on write. Seed values stay float64.
- Equivalent mutants left: unlinking a doomed holder (the holder's map is already gone, so the step is a no-op), and reading the freed-key set before the row removals (a removed key can never be a new row's id: pairing by id would have claimed it).
- C# `AnyCodec.Write` refuses a map-patch value only when it runs out of stack; Go has no such limit, so a patch nested past 4096 levels is accepted by Go and could fail C#'s decode at apply time. Unreachable from restore (values come from the doc).
- Map key order: both engines list live keys in first-set order (C# `Dictionary` never removes a key, Go keeps entries). Pinned by `lift-unlisted-children-in-key-order` (a key deleted and re-set keeps its first place); this settles the round-1 UNVERIFIED note.

- Unicode: Node 26.12.1 reports `process.versions.unicode` 17.0 (ICU 78.3); Go 1.27.1 `unicode.Version` 17.0.0; local Node 24.13 is 16.0. .NET 10.0.11's table is what Go segments with (not Go's or ICU's), because C# uses StringInfo.
