# Managed Yjs Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace YDotNet in Blok.Server with a pure-managed C# engine that speaks the Yjs v1 update format exactly as browser Yjs 13.6.x does, so the server has no native code, cannot be aborted by document data, and is independent of yrs.

**Architecture:** A `Blok.Server.Yjs` namespace inside the existing `Blok.Server` project: lib0 codec → standalone v1 update decoder → struct store with YATA integration, delete sets, pending retention → v1 encoder with state vectors and diffs → `YMap`/`YArray` read+write → `YDoc` with transactions and one emitted update per transaction. The converter and the room move to it behind the existing `ICollabDocConverter` seam; YDotNet and its native build matrix are deleted at the end. Every layer is pinned to fixtures generated by the real yjs, in both directions.

**Tech Stack:** C# / .NET 10.0, xUnit, System.Text.Json; Node 24 + yjs 13.6.32 + lib0 0.2.117 for fixture generation and replay.

**Spec:** `docs/plans/2026-09-02-ydotnet-replacement-research.md` (§2 inventory, §3 engine design, §4 wire facts and traps, §5–6 decision).

## Global Constraints

- Work directly on `main`. No branch, worktree, detached checkout, or stash.
  Stage by path only; the tree is shared with other sessions.
- TDD: write the named test, run it red, write the smallest code, run it
  green. Run only the tests you added while developing.
- `dotnet` commands run from `packages/server/dotnet`; local restores need
  `-p:NuGetAudit=false` on the command line (never in config).
- `TreatWarningsAsErrors`, analyzers at `latest-recommended`, and the CI
  coverage gate (80% lines and branches) apply to every new file.
- No new NuGet packages. No `package.json` or config changes; new scripts run
  by path.
- Interop law: the engine must decode every struct real yjs can emit, produce
  identical JSON after identical operations, produce byte-identical state
  vectors, and every update it emits must be accepted by a fresh real yjs doc
  with identical resulting JSON. Update bytes themselves are not required to
  be byte-identical.
- Never special-case `length == 1`; Y.Text arrives later on the same code.
- The first release ships **without** item merging and without GC of deleted
  items (a server that never merges is still correct, only fatter). Both are
  additive later.
- Strings: NUL is ordinary data everywhere. Invalid UTF-8 rejects the whole
  update (lib0 decodes with `fatal: true`).
- Every wave leaves main green, is committed by path, rebased onto origin
  (`git pull --rebase`, never merge, never stash), and pushed before the next.

## Locked Decisions

1. Location: `packages/server/dotnet/Blok.Server/Yjs/` (namespace
   `Blok.Server.Yjs`, `internal`), tests under `Blok.Server.Tests/Yjs/`. No
   new project or package.
2. Values: engine values are plain CLR objects — `string`, `bool`, `double`,
   `long` (tag 125), `System.Numerics.BigInteger` (tag 122), `byte[]` (116),
   `JsonObject`/`JsonArray` from `System.Text.Json.Nodes` for tags 118/117,
   `YMap`/`YArray`/`YText` for shared types, `null`, and `YUndefined.Instance`
   (tag 127). Number tag on write follows yjs exactly: integer with
   |n| ≤ 0x7FFFFFFF → 125; value that survives a float32 round-trip → 124;
   else 123.
3. One transaction → one emitted v1 update (`YDoc.UpdateEmitted` with
   `Local` true for the server's own writes, false for applied remote
   updates). The room's `applyingRemote` flag disappears.
4. Pending structs and the pending delete set are kept as decoded in-memory
   structs (not v2 bytes as yjs does), re-tried inside the same transaction
   until no progress, and **included** in diffs via a normaliser that emits
   `Skip` structs for gaps and never lists one client twice.
5. `YDoc.HasPending` is the health signal; compaction includes pending (the
   documented data loss in `CompactLocked` disappears; its test flips).
6. Client id: random uint32 at construction; regenerated when a remote
   transaction advances the local client's clock (yjs does the same).
7. Delete cascade: deleting an item whose content is a shared type deletes
   every descendant, as `ContentType.delete` does.
8. Foreign content (Y.Text, XML, Doc, Binary, Format, Embed, JSON) decodes,
   integrates, stores, and re-encodes; only `YMap`/`YArray` have a write API.
   Export renders a foreign type as its string form, as today.
9. Fixtures: a new Node generator writes `test/unit/server-conformance/
   fixtures/yjs-engine/` (beside `sync-frames.json`, never under
   `fixtures/collab/`). Every positive byte sequence comes from real yjs;
   a separate `negative.json` is hand-assembled and says so.
10. Both directions are tested: Node → C# (expected JSON, state vector, and
    `hasPending` per step, computed by a real yjs doc fed the same delivery
    schedule) and C# → Node (a replay script applies the engine's bytes to a
    fresh yjs doc; the C# test spawns `node`, which CI already has).
11. YDotNet leaves in the last wave, together with the musl CI job, the Host
    csproj override, the single-file native flag, the Docker extraction env,
    the `NETSDK1206` suppression, and the runtime probe tests.

Rules the generator must honour:

- Every `update` and every expected `sv`/`json` comes from real yjs
  (`Y.encodeStateAsUpdate`, `Y.encodeStateVector`, `doc.toJSON()`,
  `doc.store.pendingStructs !== null || doc.store.pendingDs !== null`).
  `structs.json` expected structures come from `Y.decodeUpdate` (exported by
  yjs) rendered to JSON with content refs and payloads.
- Client ids are fixed per doc (`doc.clientID = 1000/1001/1002`) so bytes are
  deterministic; gc is left at its default (true) so GC structs appear; one
  scenario sets `gc: false` explicitly to pin the other encoding.
- `structs.json` must include: map set (Any), nested Y.Map and Y.Array
  (Type), `Y.Array.from` of N strings (one item of length N), array of
  objects, array containing null (stays Any 117), grid `__rows/__rowKeys`,
  a key overwrite (item with origin and NO parentSub on the wire), a GC
  struct (delete then a second update after GC), a Skip struct (deliver
  clock 2 before clock 1, then `encodeStateAsUpdate` of the receiver), a
  Y.Text with `insert`, `format` and `insertEmbed` (refs 4, 6, 5), a
  Y.XmlFragment/XmlElement/XmlText, a Uint8Array leaf (tag 116 inside Any),
  a bigint leaf, `-0`, `NaN`, `Infinity`, 2^31, a NUL-bearing key and value,
  astral characters, and an update carrying two clients.
- `negative.json` is hand-assembled and its header says so: truncated
  varstring, varuint over 2^53, invalid UTF-8 in a key, trailing garbage
  after the delete set, a client listed twice, unknown content ref 11,
  info byte with the parentSub bit but no origin bits and no parent bytes, a
  v2 update (leading `00`).
- `scenarios.json` covers: concurrent map set on one key (LWW by client id),
  concurrent array insert at one index from three clients (YATA), out-of-
  order and duplicate delivery, delete of a block whose `data` holds a grid
  (cascade), a doc with `gc: false`, NUL strings, `Y.Array.from` runs that
  get split by a later insert into the middle.
- `fuzz/` holds 50 seeds × ~80 ops each from a mulberry32 PRNG; the op mix
  and delivery schedule (reorder, duplicate, delay) are stated in the file.
- `manifest.json` lists every file and the yjs/lib0 versions.
- The freshness test regenerates into a temp dir and asserts byte equality
  with the committed fixtures, like `collab-fixtures.freshness.test.ts`.

{
  public abstract byte Ref { get; }          // 1..9

internal enum DecodedStructKind { Item, Gc, Skip }

internal sealed record DecodedStruct(

    string? ParentRoot, YId? ParentId, string? ParentSub, YContent? Content);

Decode rules (research §3.3 and §4): info bits 0x80 origin, 0x40 right
origin, 0x20 parentSub; parent info and parentSub are present only when
neither origin bit is set; `Skip` length is a raw varuint; GC uses `readLen`;
a client listed twice is an error (yjs would overwrite silently); trailing
bytes after the delete set are an error; a v2 layout (first byte 0 and second
byte 0 where a client count and a struct count are expected) is rejected as
`v2 update`.
