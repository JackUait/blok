# Managed Yjs Engine Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Replace YDotNet in Blok.Server with a pure-managed C# engine that speaks the Yjs v1 update format exactly as browser Yjs 13.6.x does, so the server has no native code, cannot be aborted by document data, and is independent of yrs.

**Architecture:** A `Blok.Server.Yjs` namespace inside the existing `Blok.Server` project: lib0 codec → standalone v1 update decoder → struct store with YATA integration, delete sets, pending retention → v1 encoder with state vectors and diffs → `YMap`/`YArray` read+write and a minimal `YText` → `YDoc` with transactions and one emitted update per transaction. The converter and the room move to it behind the existing `ICollabDocConverter` seam in one wave; YDotNet and its native build matrix are deleted at the end. Every layer is pinned to fixtures generated by the real yjs, in both directions, plus a corpus of yrs-encoded bytes captured before the native binding leaves.

**Tech Stack:** C# / .NET 10.0, xUnit, System.Text.Json; Node 24 + yjs 13.6.32 + lib0 0.2.117 for fixture generation and replay.

**Spec:** `docs/plans/2026-09-02-ydotnet-replacement-research.md` (§2 inventory, §3 engine design, §4 wire facts and traps, §5–6 decision). Reviewed 2026-09-02 by three parallel read-only agents; their verified corrections are folded in.

## Global Constraints

- Work directly on `main`. No branch, worktree, detached checkout, or stash.
  Stage by path only; the tree is shared with other sessions.
- TDD: write the named test, run it red, write the smallest code, run it
  green. Run only the tests you added while developing.
- `dotnet` commands run from `packages/server/dotnet`; local restores need
  `-p:NuGetAudit=false` on the command line (never in config); `dotnet format`
  locally needs `--no-restore` (CI runs it plain).
- `TreatWarningsAsErrors`, analyzers at `latest-recommended`, nullable, and
  `EnforceCodeStyleInBuild` apply. The engine is `internal`;
  `Blok.Server/Properties/AssemblyInfo.cs` already grants the two test
  assemblies, so externally-visible-only CA rules do not fire. The CI
  coverage gate is solution-aggregate (80% lines and branches over
  `+Blok.Server*;-*.Tests`), checked at the Wave 3 gate and at the end.
- No new NuGet packages. No `package.json` or config changes; new scripts run
  by path.
- Interop law: the engine must decode every struct real yjs can emit, produce
  identical JSON after identical operations, produce byte-identical state
  vectors, and every update it emits must be accepted by a fresh real yjs doc
  with identical resulting JSON. Update bytes themselves are not required to
  be byte-identical, except decode→re-encode without merging.
- Never special-case `length == 1`; Y.Text formatting arrives later on the
  same code.
- The first release ships **without** item merging (a server that never
  merges is still correct, only fatter; additive later) but **with** content
  GC of deleted items (`tryGcDeleteSet`: a deleted item's content becomes
  `ContentDeleted`, a deleted subtree's items become GC structs). Without it
  the server grows without bound and re-sends every deleted payload to every
  joiner; it needs no `_mergeStructs`.
- Strings: NUL is ordinary data everywhere in the engine. Invalid UTF-8
  rejects the whole update (lib0 decodes with `fatal: true`).
- Every wave leaves main green, is committed by path, rebased onto origin
  (`git pull --rebase`, never merge, never stash), and pushed before the next.

## Locked Decisions

1. Location: `packages/server/dotnet/Blok.Server/Yjs/` (namespace
   `Blok.Server.Yjs`, `internal`), tests under `Blok.Server.Tests/Yjs/`. No
   new project or package.
2. Values: engine values are plain CLR objects — `string`, `bool`, `double`
   (every JS number, so `-0` survives; the write tag follows yjs's rule:
   integer with |n| ≤ 0x7FFFFFFF → 125, float32-round-trippable → 124, else
   123), `System.Numerics.BigInteger` (122, decode-only), `byte[]` (116,
   decode-only), `AnyObject` (118: an insertion-ordered list of key/value
   pairs) and `AnyArray` (117: `IReadOnlyList<object?>`) for nested plain
   values so `undefined`, bigint and bytes survive a decode→re-encode,
   `YMap`/`YArray`/`YText` and XML placeholders for shared types, `null`, and
   `YUndefined.Instance` (127). `System.Text.Json` nodes appear only in the
   converter: `DocReader` lowers `AnyObject`/`AnyArray` to `JsonObject`/
   `JsonArray` and drops undefined-valued keys exactly as today; the write
   path lowers every JSON number to `double` and never produces a bigint.
3. One transaction → one emitted v1 update (`YDoc.UpdateEmitted` with
   `Local` true for the server's own writes, false for applied remote
   updates). The room's `applyingRemote` flag disappears. `YDoc` holds no
   native resource and is not disposable; the room unsubscribes with `-=`.
4. Pending structs and the pending delete set are kept as decoded in-memory
   structs (not v2 bytes as yjs does) together with a `Missing` state
   vector maintained exactly as yjs does: a same-client gap records
   `missing[client] = clock − 1`, a dependency gap records
   `missing[dep] = GetState(dep)`, minimum wins. A retry runs only when some
   `missing[c] < GetState(c)`, re-integrates the whole parked set with
   `Missing` recomputed from scratch, inside the same transaction, until no
   progress. Parking dedupes by `(client, clock range)` because duplicate
   deliveries are expected. Pending structs (including their `Skip`s) are
   **included** in diffs via a normaliser that emits `Skip` structs for gaps
   and never lists one client twice, and the emitted delete set is the
   store's delete set **plus** `PendingDs`. Root parents stay strings until
   each integration attempt resolves them through `Doc.Get(name)`, so a
   placeholder upgrade cannot orphan a parked struct.
5. `YDoc.HasPending` is the health signal; compaction includes pending (the
   documented data loss in `CompactLocked` disappears; its test flips).
6. Client id: random uint32 at construction; regenerated when a remote
   transaction advances the local client's clock (yjs does the same).
7. Delete cascade: deleting an item whose content is a shared type deletes
   every descendant, as `ContentType.delete` does.
8. Foreign content (Y.Text, XML, Doc, Binary, Format, Embed, JSON) decodes,
   integrates, stores, and re-encodes; `ContentJson`, `ContentEmbed` and
   `ContentFormat` keep the **raw wire JSON string** for re-encoding (v1
   writes `JSON.stringify` output as a varstring and `System.Text.Json`
   escapes differently), parsing it only on read. Write packing follows yjs:
   `Array.Insert` packs `null`/`bool`/`double`/`string`/`AnyObject`/`AnyArray`
   into `ContentAny`, flushes `byte[]` into `ContentBinary` and a shared type
   into `ContentType`, and throws for anything else (`YUndefined`,
   `BigInteger`); `Map.Set` packs the same set plus `YUndefined` into a
   length-one `ContentAny`. `YText` gets a **minimal** write API
   (`Insert`, `Delete`, `ToString`; no formatting) because the room's whole
   test harness is built on `doc.Text("content")`, and it is the base for
   carets later. XML types are placeholders: `YXmlText` exports its string,
   `YXmlElement`/`YXmlFragment` export `""` (documented divergence; no Blok
   client writes them) rather than making a room unexportable.
9. NUL policy: the engine stores and exports NUL intact; the room does **not**
   drop a NUL-bearing update (the sender's state vector would cover it and
   every SyncStep2 would resend it forever). The pre-apply screen refuses
   only `Malformed` and `TooDeep`. `NoNul` stays on the JSON seed/edit path
   in this release (the endpoint contract is unchanged); its comments lose
   the "aborts the process" rationale.
10. Fixtures: a new Node generator writes `test/unit/server-conformance/
    fixtures/yjs-engine/` (beside `sync-frames.json`, never under
    `fixtures/collab/`). Every positive byte sequence comes from real yjs
    over raw `Y.Doc`s with pinned client ids (never the Blok client store,
    whose nanoid row keys are not deterministic); `negative.json` is
    hand-assembled and says so; `yrs-compat.json` is captured from live
    YDotNet before it is deleted. **The JSON oracle is never `doc.toJSON()`**:
    a root created by integration is an untyped placeholder that serialises
    to nothing, `JSON.stringify` throws on bigint and erases NaN/−0/Infinity/
    undefined, and `Y.Text.toJSON()` drops embeds and formats. Every case
    carries `"roots": {"name": "map"|"array"|"text"}`, and one shared
    renderer `scripts/yjs-engine-render.mjs` materialises the roots with
    `doc.get(name, Y.Map|Y.Array|Y.Text)` and emits sentinels the C# side
    reproduces: `{"$bigint":"1"}`, `{"$u8":"AQID"}`,
    `{"$num":"NaN"|"-0"|"Infinity"|"-Infinity"}`, `{"$undefined":true}`,
    `{"$text": text.toDelta()}`, `{"$xml": fragment.toString()}`.
11. Both directions are tested: Node → C# (expected JSON, state vector, and
    `hasPending` per step, computed by a real yjs doc fed the same delivery
    schedule) and C# → Node (a replay script applies the engine's bytes to a
    fresh yjs doc; the C# test spawns `node`, which the CI server job has —
    `setup-node-deps` runs before .NET).
12. The converter port and the room swap land in **one** wave and one
    commit: `ICollabDocConverter` has one consumer chain (`CollabRoom`,
    `CollabRoomManager`, two `FakeDocConverter`s), so a half-typed seam
    cannot build.
13. YDotNet leaves in the last implementation wave together with every touch
    point listed in Task 5.3.

Rules the generator must honour:

- Every `update` and every expected `sv`/`json` comes from real yjs
  (`Y.encodeStateAsUpdate`, `Y.encodeStateVector`, `doc.toJSON()`,
  `doc.store.pendingStructs !== null || doc.store.pendingDs !== null`) over
  raw `Y.Doc`s with `doc.clientID` pinned (1000/1001/1002), never through the
  Blok client store. `structs.json` expected structures come from `Y.decodeUpdate`, rendered
  by the generator itself (its `ds.clients` is a `Map` that `JSON.stringify`
  renders as `{}`; content refs come from `content.getRef()`; `ContentAny`
  exposes `arr`; a root parent is a bare string and a nested parent an `ID`).
- gc is left at its default (true) so GC structs appear; one scenario sets
  `gc: false` explicitly to pin the other encoding.
- `structs.json` must include: map set (Any), nested Y.Map and Y.Array
  (Type), `Y.Array.from` of N strings (one item of length N), array of
  objects, array containing null (stays Any 117), grid `__rows/__rowKeys`,
  a key overwrite (item with origin and NO parentSub on the wire), a GC
  struct (delete a `Y.Map` or `Y.Array` **that has children**; its children
  become GC structs in that doc's next `encodeStateAsUpdate`; a scalar
  delete yields `ContentDeleted`, never GC), a Skip struct (deliver
  clock 2 before clock 1, then `encodeStateAsUpdate` of the receiver), a
  Y.Text with `insert`, `format` and `insertEmbed` (refs 4, 6, 5), a
  Y.XmlFragment/XmlElement/XmlText, a Uint8Array leaf (tag 116 inside Any),
  a bigint leaf, `undefined` inside an object, `-0`, `NaN`, `Infinity`,
  2^31, a NUL-bearing key and value, astral characters, and an update
  carrying two clients.
- `negative.json` is hand-assembled and its header says so: truncated
  varstring, varuint over 2^53, invalid UTF-8 in a key, trailing garbage
  after the delete set, a client listed twice, unknown content ref 11,
  info byte with the parentSub bit but no origin bits and no parent bytes, a
  v2 update (leading `00`).
- `scenarios.json` covers: concurrent map set on one key (LWW by client id)
  from two and from three clients, concurrent array insert at one index from
  three clients (YATA), out-of-order and duplicate delivery, a delete
  concurrent with an insert into the same run (drives clean-start/clean-end
  splitting during integration), a delete set naming clocks the receiver has
  not got (`pendingDs`), an update carrying only a delete set, deleting then
  re-inserting a key, delete of a block whose `data` holds a grid (cascade),
  a doc with `gc: false`, NUL strings, `Y.Array.from` runs split by a later
  insert into the middle, a Y.Text root with format and embed, and
  `engineWrites` steps while the engine holds pending structs (the edit-API
  path, which exercises the normaliser over local structs interleaved with
  pending).
- `fuzz/` holds 50 seeds × ~80 ops each from a mulberry32 PRNG; the op mix
  and delivery schedule (reorder, duplicate, delay, engine writes) are
  stated in the file.
- `manifest.json` lists every generated file and the yjs/lib0 versions.
- Byte determinism, which `collab-fixtures` does NOT have, requires: never
  import `src/components/modules/yjs/*` (nanoid lives there); grids built
  from raw `Y.Map`/`Y.Array` with literal `__rowKeys`; any subdoc created
  with an explicit `guid`; every `doc.clientID` asserted unchanged at the
  end (yjs regenerates it when a remote transaction advances the local
  clock); `manifest.json` versions asserted equal to
  `node_modules/{yjs,lib0}/package.json` so a bump goes red before bytes
  drift. The generator takes `--out <dir>`; the freshness test (marked
  `// @vitest-environment node`, with an explicit 120 s timeout) regenerates
  into a temp dir and asserts byte equality with the committed files,
  following `generate-sync-frames.mjs`'s pinned-client-id precedent.

Decode rules (research §3.3 and §4): info bits 0x80 origin, 0x40 right
origin, 0x20 parentSub; parent info and parentSub are present only when
neither origin bit is set; `Skip` length is a raw varuint; GC uses `readLen`;
any length above `int.MaxValue` is malformed at decode (never an overflow);
`ContentType` reads one varuint typeRef and, for refs 3 (`YXmlElement`) and
5 (`YXmlHook`), one extra varstring; `ContentJson` is `writeLen` + N
varstrings of JSON (`'undefined'` sentinel), `ContentEmbed` one varstring of
JSON, `ContentFormat` varstring key + varstring JSON, `ContentDoc` varstring
guid + `Any` opts, `ContentBinary` a copied byte array; a client listed twice
is an error (yjs would overwrite silently); trailing bytes after the delete
set are an error. There is **no** byte sniff for v2: `00 00` is the
legitimate empty v1 update the room sends on every sync; a v2 update is
simply one that fails to parse as v1. The `Any` nesting cap is a stack guard
(4096), not policy; the inspector's `TooDeep` at 256 is the room's policy.
