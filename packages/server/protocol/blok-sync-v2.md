# `blok-sync.v2` wire protocol

Normative specification of the Blok collaboration WebSocket protocol
`blok-sync.v2`. It is written so a backend outside this repository can
implement a conformant server or client from this document alone.

`blok-sync.v2` adds durable, individually acknowledged **operations** on top of
`blok-sync.v1`. Every frame type that v1 defines keeps its exact v1 bytes; v2
only adds three new outer types.

The key words MUST, MUST NOT, SHOULD and MAY are to be read as in RFC 2119.

Conformance test vectors for every frame in this document live in
`test/unit/server-conformance/fixtures/sync-frames.json` (generated by
`scripts/generate-sync-frames.mjs`). The `v2.frames` array holds valid frames
for every shape. Each `v2.negative` entry carries the outcome a conformant
decoder MUST produce for it: `malformed` for all but one, and `unknown` —
accepted and ignored, not refused — for the unknown-outer-type case. Section 10
documents both entry shapes field by field.

## 1. Notation

All frames are binary WebSocket messages. **Exactly one frame per WebSocket
message.** The primitives are the lib0 encoding used by y-protocols:

| Term | Bytes |
| --- | --- |
| `varuint(n)` | LEB128: 7 value bits per byte, little-endian groups, high bit set on every byte except the last. At most 10 bytes; the tenth byte MUST NOT carry more than the lowest bit, so the value fits 64 bits. |
| `varbytes(b)` | `varuint(length of b)` followed by the raw bytes of `b`. |
| `varstring(s)` | `varbytes(UTF-8 encoding of s)`. Identical framing to `varbytes`; the distinction is only that the payload is required to be valid UTF-8. |

A decoder MUST reject a varuint longer than 10 bytes — including an 11-byte
encoding of a small value, which some lib0 readers accept — and MUST reject a
10-byte encoding whose final byte carries any bit above the lowest, because the
value would not fit 64 bits. It MUST NOT throw on either; both are malformed
input, not exceptions.

## 2. Subprotocol negotiation

The client offers WebSocket subprotocols in this order:

```text
blok-sync.v2, blok-sync.v1, <ticket when configured>
```

A v2 server selects the highest version it supports. A v1 server selects
`blok-sync.v1`. When a server searches the offered protocols for an
authentication ticket it MUST exclude both `blok-sync.v1` and `blok-sync.v2`
from the candidates, or it will read a version token as a ticket.

A client that negotiates v1 MUST NOT claim durable acknowledgement. If it holds
undelivered v2 operations it keeps them, blocks further edits and reports
durability unavailable rather than replaying them through v1.

## 3. Frame types

| Type | Name | Direction | Introduced |
| --- | --- | --- | --- |
| 0 | sync (SyncStep1 / SyncStep2 / Update) | both | v1 |
| 1 | awareness | both | v1 |
| 2 | auth (permission denied) | server → client | v1 |
| 3 | query awareness | both | v1 |
| 100 | Blok working-set control | server → client | v1 |
| 101 | Blok limits | server → client | v1 |
| 102 | **operation** | client → server | v2 |
| 103 | **acknowledgement** | server → client | v2 |
| 104 | **rejection** | server → client | v2 |

Types 0–3, 100 and 101 are byte-for-byte identical in v1 and v2. A decoder MUST
treat an unrecognised **outer** type as an ignorable frame (skip it, keep the
connection) exactly as `y-websocket` does; it MUST NOT close the socket. An
unrecognised **sub**-type inside a known outer type is malformed.

### 3.0 The v1 frames this document depends on

v2 does not redefine these, but three v2 rules are unimplementable without
them: section 7's 1008 close names the sync frames, `lineage` comes from the
type-100 frame, and `oversized-update` is measured against the type-101 frame.
Every layout below is pinned byte-for-byte by the `frames` array in the
conformance fixture. Types 0-3 are `y-protocols` / `y-websocket` as stock
clients speak them; the outer type byte is `y-websocket`'s, since the
`y-protocols` sync and auth writers emit only the sub-type.

**Type 0 — sync**

```text
varuint(0)  varuint(subType)  varbytes(payload)
```

| Sub-type | Name | Payload |
| --- | --- | --- |
| 0 | SyncStep1 | The sender's Yjs state vector |
| 1 | SyncStep2 | A Yjs update answering a SyncStep1 |
| 2 | Update | A Yjs update broadcast on its own |

The payload MUST be at least one byte; a sub-type above 2 is malformed (an
unknown *sub*-type is an error, unlike an unknown outer type).

**Types 1-3**

```text
varuint(1)  varbytes(awarenessUpdate)          awareness, relayed verbatim
varuint(2)  varuint(0)  varstring(reason)      auth; 0 = permissionDenied, the only sub-type
varuint(3)                                     query awareness; the type byte is the whole frame
```

The awareness payload is `y-protocols/awareness`; this protocol never
interprets it. An auth reason MAY be empty.

**Type 100 — Blok working-set control** (server → client)

```text
varuint(100)  varstring({"epoch":N,"format":N,"lineage":"<32 lowercase hex>"})
```

Keys in exactly that order. `format` is the working-set schema version and MUST
be at least 1; `epoch` MUST be at least 0; `lineage` MUST match
`^[0-9a-f]{32}$`. `lineage` is the value every v2 metadata section carries, so a
server cannot serve v2 without sending this frame.

**Type 101 — Blok limits** (server → client)

```text
varuint(101)  varstring({"maxMessageBytes":N})
```

`maxMessageBytes` MUST be a positive integer. It is the cap an operation is
measured against before the server answers `oversized-update`.

Both Blok payloads keep the v1 decoder rules they shipped with; section 5's
rules are v2 metadata rules and do not retroactively change them.

### 3.1 Type 102 — Operation

```text
varuint(102)  varstring(metadata)  varbytes(update)
```

Type 102 is the only Blok frame with **two** length-prefixed sections. Types
100 and 101 carry a single `varstring`; a decoder written against their shape
will read 102's metadata and stop, leaving the update unread — the frame is not
finished at that point and such a decoder is non-conformant. The frame ends
only after the second section.

- `metadata` — canonical JSON, keys in exactly this order:

  ```json
  {"lineage":"<32 lowercase hex>","operationId":"<32 lowercase hex>"}
  ```

- `update` — the raw Yjs update the operation carries. It MUST be at least one
  byte long; a zero-length second section is malformed. The bytes are opaque to
  the framing layer.

### 3.2 Type 103 — Acknowledgement

```text
varuint(103)  varstring(metadata)
```

```json
{"lineage":"<32 lowercase hex>","operationId":"<32 lowercase hex>","serverSequence":"<decimal>"}
```

### 3.3 Type 104 — Rejection

```text
varuint(104)  varstring(metadata)
```

```json
{"lineage":"<32 lowercase hex>","operationId":"<32 lowercase hex>","code":"<code>"}
```

## 4. Metadata grammar

### 4.1 Field values

| Field | Type | Constraint |
| --- | --- | --- |
| `lineage` | JSON string | `^[0-9a-f]{32}$`. The working-set lineage announced by the type-100 control frame. |
| `operationId` | JSON string | `^[0-9a-f]{32}$`. 128 CSPRNG bits, generated once per local update, persisted with the bytes before the first send, and never regenerated on retry. |
| `serverSequence` | JSON **string** | `^(0\|[1-9][0-9]*)$` and numerically at most `18446744073709551615`. A gap-free, server-assigned position within the lineage. In a type-103 frame it MUST be at least 1. |
| `code` | JSON string | `^[a-z][a-z0-9-]{0,63}$`. The six codes in section 6 are the stable set, but a decoder MUST accept any other code matching this pattern. |

`serverSequence` is carried as a decimal **string**, not a JSON number: its
ceiling is 2^64 − 1, which no IEEE-754 double can represent exactly. The regex
forbids a leading `+`, a leading zero on a non-zero value, a sign, whitespace,
and any exponent or fraction, so the decimal text is the canonical form of the
value and two implementations always agree on it.

**Sequences start at 1.** The first operation committed on a lineage is
acknowledged with `serverSequence` `"1"`, the next with `"2"`, and so on with
no gaps. `0` therefore means *no operation has been committed on this lineage
yet*: it is the empty value for a durable-through or high-water mark. Without
this, a gap-detecting client and a foreign server disagree about whether the
first acknowledgement should have been `0` or `1`.

**In a type-103 frame `serverSequence` MUST be at least 1**, because an
acknowledgement by definition acknowledges a committed operation and `0` is
reserved for "nothing committed". A type-103 frame carrying `"0"` is malformed
under rule 12. This is a range rule layered on the grammar, not a change to it:
`^(0|[1-9][0-9]*)$` still accepts `0`, which stays a legal value of a
durable-through field, where it means something.

### 4.2 Canonical JSON

An encoder MUST emit, for each type, exactly the key set listed above, each key
exactly once, in exactly the order listed, with:

- no whitespace anywhere;
- no `\` escape sequence anywhere (every key and value is ASCII: hex digits,
  decimal digits, or a lowercase kebab-case code);
- no byte-order mark;
- no content before or after the single JSON object.

The committed fixtures pin these bytes.

**Key order is an emitter rule. Emitters MUST write the keys in the order
listed above; decoders MUST NOT depend on it.** A decoder validates the key set
and each key's uniqueness, not the sequence, exactly as the existing type-100
and type-101 decoders do — and most JSON libraries never expose key order to a
decoder at all, so an order-strict decoder would be unimplementable in them.
The `acknowledgementKeysOutOfOrder` fixture is a frame every conformant decoder
MUST accept. What a decoder MUST NOT accept, in any order, is a missing key, an
unknown key, or a repeated key.

In the fixture file each `v2.frames` entry carries a `canonical` flag.
`canonical: true` means these are the bytes an emitter produces, so an encoder
fed this frame's decoded fields MUST reproduce its bytes. The one
`canonical: false` frame is decode-only: an encoder fed its decoded fields
would rightly emit the canonical key order, so a round-trip assertion on it
would be asserting the wrong thing.

## 5. Decoder rules

A conformant decoder MUST reject a frame — report it as malformed and never act
on it — when any of the following holds. What a peer then does with the
connection is left to the implementation; the two dispositions this document
does fix are the `1008` close in section 7 and the `4503` close in section 6.1.

**Evaluation order is normative: a decoder checks these rules in ascending
numeric order and reports the first one the frame violates.** One frame can
break several rules — `{"lineage":…,"lineage" :…}` breaks both rule 8 and rule
11 — so without a fixed order two conformant decoders would attribute the same
bytes to different rules, and the `rule` field on every negative vector would
mean nothing. Order matters only for *attribution*; the frame is malformed
either way. A decoder that reports no rule at all is still conformant, but one
that reports a rule MUST report the lowest-numbered one.

**Framing**

**Rule 1.** The outer type varuint is missing, truncated, longer than 10 bytes,
or does not fit 64 bits.

**Rule 2.** Any length prefix exceeds the bytes remaining in the message. The
bounds check MUST happen **before** any allocation, so the 2 GiB update-length
prefix on the 102-byte `operationHugeUpdateLength` vector allocates nothing.

**Rule 3.** A section is missing entirely — in particular a type-102 message
that ends after its metadata section.

**Rule 4.** The type-102 update section is zero bytes long.

**Rule 5.** *Full input consumption fails at the frame level:* after the last
section of the frame, one or more bytes remain in the WebSocket message.
Exactly one frame per message; there is no trailing padding and no batching.

**Metadata**

**Rule 6.** The metadata section is not valid UTF-8. Decoding MUST be strict
(fatal on any invalid sequence) and MUST NOT silently strip a byte-order mark;
a BOM-prefixed payload is not valid JSON and is therefore rejected.

**Rule 7.** The metadata text contains a `\` byte anywhere. A conformant
encoder never emits one, so its presence marks a crafted payload.

**Rule 8.** The metadata text contains any of the four bytes JSON permits as
whitespace — `0x20` space, `0x09` tab, `0x0A` line feed, `0x0D` carriage
return — anywhere, inside a string or outside one. Section 4.2 already forbids
an encoder from emitting them.

Rules 7 and 8 **together** are what make a purely textual duplicate-key check
exact; neither alone does. Without rule 7, `{"lin\u0065age":…,"lineage":…}`
carries the key `lineage` twice while the literal token `"lineage"` appears
once. Without rule 8, `{"lineage":…,"lineage" :…}` — one space before the
second colon — does the same to a scan for `"lineage":`. Either way a second
`lineage` slips past the check and JSON last-wins hands the sender the field. A
decoder that detects duplicates structurally, from a parser that reports every
key occurrence, satisfies rule 11 without either scan; it MUST still apply
rules 7 and 8, because two conformant implementations have to agree on the same
bytes.

**Rule 9.** *Full input consumption fails at the JSON level:* the metadata text
is not exactly one complete JSON value, or any content follows it. With rule 8
in force there is no trailing whitespace to tolerate.

**Rule 10.** The top-level JSON value is not an object (an array, string,
number, boolean or `null` is malformed).

**Rule 11.** A key is missing, unknown, or appears more than once.

**Rule 12.** A value has the wrong JSON type, or a string value fails its
pattern in section 4.1 — including uppercase hex, an ID shorter or longer than
32 characters, a `serverSequence` sent as a JSON number, a `serverSequence`
with a leading zero or a sign, a `serverSequence` above
`18446744073709551615`, a `serverSequence` of `0` in a type-103 frame, or a
`code` that does not match
`^[a-z][a-z0-9-]{0,63}$` (empty, uppercase, over 64 characters, or carrying a
character outside that class).

Key **order** is not a rule and MUST NOT be a rejection reason; see section 4.2.

These rules govern v2 metadata — types 102, 103 and 104. Types 100 and 101 keep
the decoder rules they shipped with in v1; this document does not change them.

Every `v2.negative` fixture names the rule number it violates in its `rule`
field, so an implementation can assert *why* a frame was refused, not merely
that it was. The numbers are stable identifiers, which is why they are written
out rather than left to a renderer's ordered-list numbering.

A decoder MUST NOT throw on hostile input; every failure above is a value the
caller can inspect.

## 6. Rejection codes

These six code strings are stable and keep the meanings below. They are not a
closed set: a decoder MUST accept any code matching
`^[a-z][a-z0-9-]{0,63}$`, including one it does not recognise.

Refusing an unrecognised code has a liveness hole with no way out. A newer
server sends a seventh code; an older client treats the frame as malformed;
it therefore never learns the operation was rejected; the row stays in its
outbox; it is redriven on the next reconnect and rejected again, forever. So a
receiver MUST treat an unrecognised code as a **final** rejection — the same
handling as `read-only`: quarantine the operation and the remaining lineage
tail rather than retrying it.

| Code | Meaning |
| --- | --- |
| `lineage-mismatch` | The operation names a lineage the server no longer serves. |
| `read-only` | The connection has no write permission for this document. |
| `not-synced` | The operation arrived before the connection finished its sync phase. |
| `invalid-update` | The update bytes are not a Yjs update this server can apply. |
| `oversized-update` | The operation exceeds the server's configured message limit (announced in the type-101 limits frame). |
| `operation-id-conflict` | The same `operationId` was already committed with different bytes. |

`invalid-update`, `oversized-update`, `read-only` and `operation-id-conflict`
are **final**: the client quarantines the rejected operation and the remaining
lineage tail, because later Yjs updates in that lineage may depend on it. It
never silently drops them. `read-only` is on that list deliberately — a write
verdict that flips mid-typing must leave the typed content recoverable rather
than lost.

`lineage-mismatch` is resolved by the lineage-reset path: before adopting a new
lineage the client flushes its write buffer, waits for every outstanding local
append, then atomically moves every old-lineage pending row and a recovery
snapshot to quarantine, and only then resets the document. It never sends those
bytes to the new lineage.

`not-synced` is the one **transient** code. The room was not ready; the
operation was never judged invalid. A receiver keeps the operation pending and
redrives it once the sync phase completes, and it MUST NOT quarantine it.
Reconnect backoff bounds the retry, the same way it bounds the
commit-unavailable path in section 6.1.

### 6.1 Commit unavailable is not a rejection

A transient failure of the server's operation store produces **no** type-104
frame and **no** type-103 frame. The server closes every member of the document
with WebSocket status `4503` and the reason `commit unavailable, retry`. The
client keeps every pending row, quarantines nothing, and reconnects with
backoff; retrying the same `operationId` resolves the unknown commit outcome,
because a re-sent operation with the same ID and the same bytes is a duplicate
(section 7).

## 7. Write rules on a v2 socket

**Only an operation frame may carry a client write.** A raw sync SyncStep2 or
sync Update frame from the client carries no `operationId`, so the server cannot
answer it with a type-103 or a type-104. The server MUST drop such a frame and
close the connection with WebSocket status `1008` (policy violation). It MUST
NOT apply it.

Type-0 sync frames remain the **server-to-client** broadcast format, so v1 and
stock `y-websocket` readers still receive committed content. The server
broadcasts a committed update to every member including the socket that
submitted it; applying an update twice is harmless in Yjs, and this is required
when one tab submits an operation another tab created.

### 7.1 Handshake and the post-drain residual diff

v2 keeps the v1 handshake bytes and changes only what the client may send back:

1. the client sends SyncStep1 and applies the server's SyncStep2;
2. the server also sends its own SyncStep1, as in v1, and does so again after
   every inbound SyncStep1;
3. the client never answers with a raw SyncStep2. While it still holds pending
   operations it ignores the server's SyncStep1 and drains through type-102
   frames;
4. once it holds none, it sends SyncStep1 again and, against the fresh server
   state vector, wraps any **residual** local diff as one more type-102
   operation.

Step 4 is what carries edits made under an earlier v1 session — cached locally
with no operation record — onto a server that has since gained a durable store.
Without it those edits would either be lost or be uploaded outside an operation
envelope, which the write rule above forbids.

### 7.2 Idempotency

The same `operationId` with the same payload digest is a duplicate: the server
returns the original acknowledgement and neither applies nor records the
operation twice. The same `operationId` with different bytes is a terminal
conflict, answered with `operation-id-conflict`.

## 8. What an acknowledgement means

A type-103 frame means all of the following are durable in the server's
configured operation store:

- the document and lineage;
- the exact operation ID and payload digest;
- a server-assigned, gap-free sequence within that lineage;
- the authenticated actor, if the connection has one;
- the server commit time and source;
- the raw Yjs update needed to replay the operation.

It does **not** mean:

- every peer has received the broadcast;
- the operation won every CRDT conflict;
- any consumer-side projection has completed;
- the browser has made origin storage immune to eviction;
- a visible DOM edit and its asynchronous local write were one atomic act;
- an intentional reset can never start a new history.

A connection being live and content-synced is a separate fact from local edits
being saved, and the two are reported separately. A rejected operation or a
broken local store is not a terminal connection state: the socket can still
receive.

## 9. Compatibility

| Client | Server | Result |
| --- | --- | --- |
| v1 | v1 | v1 behaviour; no client save receipt |
| v1 | v2 | v1 selected; on a journal-backed document the server still journals each update before broadcasting it, so a v1 update waits for the append; the client gets no receipt |
| v2 | v1 | v1 selected; the client reports durability unavailable and never reports saved |
| v2 | v2 | Exact durable operation acknowledgements |
| stock `y-websocket` | v2 | Standard y-protocol sync on the v1 write path; a journal-backed document journals its writes; no receipt and no durability claim |

## 10. Conformance fixture schema

`test/unit/server-conformance/fixtures/sync-frames.json` is generated, never
hand-edited. Its `v2` object is:

| Field | Meaning |
| --- | --- |
| `protocol` | `"blok-sync.v2"` |
| `lineage`, `operationId` | The pinned ids every v2 vector uses |
| `rejectionCodes` | The six stable codes of section 6, in order |
| `rejectionCodePattern` | `^[a-z][a-z0-9-]{0,63}$` — read it from here rather than retyping it |
| `frames` | Frames a decoder MUST accept |
| `negative` | Crafted frames, each carrying the outcome a decoder MUST produce for it |

### `v2.frames` entries

| Field | Type | Meaning |
| --- | --- | --- |
| `name` | string | Stable identifier; use it to look a vector up, never the array index |
| `messageType` | integer | 102, 103 or 104 |
| `canonical` | boolean | `true`: an encoder fed this frame's decoded fields MUST reproduce `frameHex` exactly. `false`: decode-only — see section 4.2 |
| `description` | string | Prose; what the vector is for |
| `frameHex` | hex string | The complete WebSocket message |
| `metadataJson` | string | The exact UTF-8 text of the metadata section, byte for byte |
| `metadata` | object | The same metadata parsed, for typed assertions |
| `updateHex` | hex string | Type 102 only: the second section's bytes |

### `v2.negative` entries

| Field | Type | Meaning |
| --- | --- | --- |
| `name` | string | Stable identifier |
| `messageType` | integer, optional | The outer type, when the frame reaches one. Absent on `outerVarUintTooLong`, which fails before any type is read |
| `expect` | `"malformed"` \| `"unknown"` | The outcome a decoder MUST produce. `"unknown"` means accepted and ignored, not refused |
| `rule` | integer, optional | The **lowest-numbered** section-5 decoder rule the frame violates, per that section's evaluation order. Absent when `expect` is `"unknown"`, which violates none |
| `description` | string | What is wrong, and why the case exists |
| `frameHex` | hex string | The complete WebSocket message |
| `metadataJson` | string, optional | The metadata text, when the section is valid UTF-8 |

Every one of the twelve rules in section 5 has at least one negative vector, so
a decoder can be exercised rule by rule rather than in aggregate. A decoder that
refuses every negative vector is not yet conformant: it must refuse each one for
the `rule` the entry names.

`rule` is always the **lowest-numbered** rule the frame violates, per the
evaluation order in section 5. Two vectors deliberately violate more than one:

| Vector | Rules violated | `rule` |
| --- | --- | --- |
| `operationEscapedDuplicateKey` | 7, 11 | 7 |
| `operationWhitespaceDuplicateKey` | 8, 11 | 8 |

Both carry the key `lineage` twice, so a decoder that detects duplicates
structurally sees rule 11 as well — which is correct, and is exactly why the
order is normative rather than advisory. Every other vector violates exactly
one rule.
